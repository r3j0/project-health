# DB 설계와 운영

PostgreSQL 17과 Prisma 7.10을 사용한다. 정밀한 측정값, 고유 키·외래키, 트랜잭션과 명시적인 마이그레이션을 사용하는 구조다.

## 계정과 측정 데이터

- `users`: id·email·password·created_at·updated_at의 계정 정보. 이메일은 정규화한 값으로 유일하며 이메일 인증 API가 입력 검증·Argon2id 해싱·응답 필드 제한을 처리한다. 이메일 소유 확인과 소셜 로그인은 후속 범위다.
- `auth_sessions`, `auth_refresh_tokens`, `auth_rate_limits`: 인증 세션, refresh token 해시·사용 이력, DB 기반 요청 제한. [인증 API](auth-api.md)를 참고한다.
- `measurement_catalogs`: 공식 자료 확인일과 버전. 실제 평가 기준 시행일과 구분한다.
- `measurement_definitions`: 출처 URL, 검사 방법, 단위, 적용 나이, 정수·소수·값 범위. 공개 검사 목록을 기준 데이터로 보관하며 사용자 결과는 생성하지 않는다.
- `measurements`: 사용자 ID, 실제 측정일, 측정 당시 나이, 원문 등급, 카탈로그 버전, revision.
- `measurement_items`: 검사별 실제 입력값. 고정 정밀도가 없는 NUMERIC을 사용하여 저장 시 자릿수 반올림을 피한다. Prisma Decimal은 JSON 직렬화 시 문자열이므로 후속 API 계약에도 이를 명시해야 한다.
- `measurement_create_requests`: 사용자별 생성 요청 키·정규화한 입력 해시·생성한 기록 연결. 기록 삭제 시 연결만 null로 바꿔 생성 재시도가 삭제를 되돌리지 않게 한다. 계정 삭제 시 함께 지운다.

Prisma 관계를 통한 조회는 비밀번호 필드를 포함할 수 있다. 인증 발급 응답은 기존 공개 4개 필드를 직렬화하고, `/api/v1/auth/me`는 그 필드와 본인의 온보딩·재화·현재 운동 배정을 반환한다. 비밀번호·세션은 명시적 select/serializer로 제외한다.

- `user_preferences`: userId PK/FK, 단일 선택 운동량 enum 기본 standard, nullable 목적 enum 초기 null, 생성·실제 변경 시각. [운동 설정 API](user-preferences-api.md)의 가입·배포·부분 수정 계약을 따른다.
- `user_currencies`: userId PK/FK, balance INTEGER DEFAULT 0, 비음수 CHECK. 허용 잔액 0~2,147,483,647.
- `workout_curricula`: 공용 운동 1회분 정의의 최소 식별 구조. 콘텐츠·추천 seed 없음, 정의 수정 금지.
- `user_curriculum_assignments`: 배정·완료 상태, 시각, 요청 키, 이력. 현재는 nullable currentForUserId UNIQUE로 표시하며 소유자 일치 CHECK가 있다. 사용자 행 잠금으로 다음 배정과 완료를 직렬화한다.

신규 가입은 User·재화·운동 설정·세션을 같은 트랜잭션으로 만든다. 기존 사용자의 재화는 마이그레이션 6에서 0으로 백필하며 마이그레이션 7은 기존 잔액을 유지한다. 재화 행 누락 시 상세 조회는 503이다. 모든 소유 데이터·세션·토큰은 User 삭제의 FK CASCADE로 원자적으로 삭제한다. 공용 카탈로그·커리큘럼은 보존한다. 상세 제약과 내부 서비스 계약은 [사용자 API](users-api.md)를 따른다.

## DB가 보장하는 무결성

외래키로 실제 사용자·카탈로그·검사와 연결한다. 기록과 항목의 카탈로그 버전이 일치해야 하고 검사 단위도 일치해야 한다. 같은 회차의 검사 코드는 중복되지 않는다. 공식 검사 정의는 수정·삭제하지 않고 새 버전으로 추가한다.

Prisma가 표현하지 못하는 제약은 마이그레이션 SQL에 있다. 측정 당시 연령, 정수 횟수, 숫자 범위, 유한 숫자, 최소 한 항목을 검증한다. 부모와 항목을 같은 트랜잭션에서 만들 수 있도록 일부 제약은 커밋 시 검증한다. 항목 변경은 부모를 잠가 동시 삭제로 빈 기록이 생기지 않도록 한다. 트랜잭션의 중간에 항목을 교체할 수 있지만 최종 빈 기록은 커밋할 수 없다.

측정 수정 API는 `If-Match`와 현재 revision을 비교하고 전체 변경과 같은 트랜잭션에서 revision을 증가시킨다. 생성은 사용자별 요청 키로 중복을 막고, 모든 개인 기록 조회·변경은 인증된 사용자 ID로 제한한다. Decimal 값은 API에서도 문자열로 처리한다. [측정 API 계약](measurements-api.md)을 참고한다. 종목별 평가는 `measurement_items.evaluation` JSONB에 입력과 같은 트랜잭션으로 저장한다. null은 기존 미평가 데이터이며 조회만으로 채우지 않는다.

8. `20260923000100_self_assessment_evaluation`: 간이측정 등록 방식, 항목 평가 JSONB, 21개 정의의 카탈로그를 추가한다.
9. `20260924000100_retire_self_curl_up`: 신규 입력에서 제외한 성인 `self_curl_up`을 빼고 20개 정의의 새 카탈로그를 추가한다. 기존 카탈로그·측정·평가·요청 이력은 보존한다.

10. `20260926000100_user_preferences`: 두 enum·설정 테이블과 CASCADE FK를 추가한다. 기존 사용자 기본 standard/null을 실제 설정 생성 시각으로 백필하며 중복 초기화는 값을 보존한다. 가입 중지와 서버 교체 순서는 [운동 설정 배포 안내](user-preferences-api.md#마이그레이션과-배포)를 따른다.

마이그레이션 1·2를 이미 로컬 DB에 적용한 뒤 계정 컬럼이 확정되어 3으로 추가했다. 기존에 적용한 파일을 다시 쓰거나 DB를 초기화하지 않았다. 사용자 ID만 있는 기존 운영 행이 존재한다면 마이그레이션 3 적용 전에 실제 이메일을 확보하는 별도 이행 작업이 필요하다. 마이그레이션 4는 기존 계정 행이나 비밀번호를 변경하지 않는다.

Prisma 스키마를 바꾼 후에는 개발 마이그레이션 초안을 확인하고 필요한 SQL 제약을 추가한다. 기존 마이그레이션은 수정하지 않는다. PostgreSQL 트리거·CHECK는 Prisma 스키마에 전부 표시되지 않으므로 SQL과 실제 DB 통합 테스트가 함께 기준이 된다. 운영에서 `db push`나 `migrate reset`으로 적용하지 않는다.

### 사용자 기능과 범위 정정 적용 순서

개발·운영은 각 환경의 `DATABASE_URL`, 통합 테스트는 반드시 별도 DB의 `TEST_DATABASE_URL`을 사용한다. 이번 코드 작업은 전용 테스트 DB에만 마이그레이션을 적용하며 개발/운영 데이터베이스를 변경하지 않는다.

2026-09-26 UserPreference 배포에는 아래 공통 명령 외에 **가입 중지·진행 중 가입 완료 → 마이그레이션 → 모든 구버전 서버 교체 → 누락 점검 → 가입 재개**가 필요하다. [운동 설정 배포 안내](user-preferences-api.md#마이그레이션과-배포)의 순서와 중단된 배포 복구 INSERT를 함께 따른다.

```bash
# backend/에서 대상 환경 DATABASE_URL을 확인한 뒤 실행
npm ci
npm run db:validate
npm run db:generate
npm run db:status
npm run db:migrate:deploy
npm run build
npm run start:prod
```

운영 배포는 기존 DB 백업/복구 절차를 따르고 검토된 마이그레이션을 새 코드 시작 전에 한 번 적용한다. 각 SQL은 BEGIN/COMMIT으로 적용된다. 최신 정정 SQL은 폐기한 선호/목적/목표의 컬럼·테이블과 저장 데이터도 삭제한다. 이전 구현을 사용하는 클라이언트는 새 계정 PATCH 계약과 재로그인 처리를 함께 반영해야 한다. 기존 이메일·비밀번호·ID·측정/항목·인증 세션·요청 이력·잔액·배정은 보존한다. 공용 운동이나 사용자 측정 결과를 생성하지 않는다. 대규모 users 테이블에서는 ALTER/백필/제거의 잠금·실행 시간을 스테이징에서 확인하고 배포 창을 잡는다. 실패 시 원인을 해결해 정식 마이그레이션 복구 절차를 따르며 reset/db push를 사용하지 않는다.

`db:generate` 결과는 생성 코드이며 직접 수정하지 않는다. 원시 SQL 행 잠금도 DatabaseService의 스키마별 테이블 식별자를 사용해 Prisma의 `schema`와 일치시킨다.

## 연결·테스트

앱은 초기화 단계에서 환경변수의 접속 주소로 `SELECT 1`을 실행해 실제 연결을 확인한다. 연결 확인에 실패하면 풀을 정리하고 서버 시작을 중단한다. 정상 종료 시에도 풀을 정리한다. 설치된 PostgreSQL 어댑터의 TIMESTAMPTZ 입출력이 UTC를 가정하므로 각 풀 연결의 startup options에 TimeZone=UTC를 마지막으로 지정한다. 기존 연결 옵션은 보존하며 DB 전역 설정은 바꾸지 않는다. 풀 크기는 프로세스당 최대 5개, 연결 제한 5초, 쿼리 제한 10초다. 프로세스 수와 운영 DB의 연결 한도를 함께 고려해 조정한다. 접속 주소·비밀번호를 로그나 상태 확인 응답에 출력하지 않는다.

전용 테스트 DB에 임시 스키마를 만들고 모든 마이그레이션을 두 번 실행해 재적용도 확인한다. 기존 데이터 업그레이드 검사에서는 별도 임시 스키마에 이전 마이그레이션과 사용자·측정·세션 fixture를 넣는다. 최초 확장 후 선호/목적/목표·재화 잔액·운동 배정 fixture도 저장한 뒤 범위 정정 SQL을 적용한다. 폐기 데이터 제거, 계정/측정/인증/잔액/배정 보존, 재화 백필, 기존 사용자 온보딩을 확인한다. 테스트 종료 시 생성한 임시 스키마만 삭제한다. 중간 프로세스 강제 종료 시 `test_` 접두사의 잔여 스키마가 남을 수 있으며 자동으로 다른 스키마를 삭제하지 않는다.

## 의존성 고정

Prisma Client·PostgreSQL 어댑터·CLI를 7.10.0으로 맞췄다. 이 버전의 하위 패키지에서 보고된 재귀 병합 및 MySQL 드라이버 취약점 때문에 `@prisma/config`의 `deepmerge-ts`를 8.0.2, Prisma의 `mysql2`를 3.24.4로 제한해 override한다. 현재 서비스 DB는 PostgreSQL이다. 의존성 갱신 시 override 필요성과 공식 지원 범위를 다시 확인하고 스키마 생성·마이그레이션·실제 DB 테스트를 함께 실행한다.

## 2026-09-23 간이측정·평가 마이그레이션

`20260923000100_self_assessment_evaluation`은 등록 방식 enum에 `self_assessment`, 측정 항목에 nullable JSONB `evaluation`을 추가한다. 기존 카탈로그 19개는 유지하고 21개 항목의 `nfa100-2026-09-23`을 추가한다. 기존 기록·원문 등급·계정·요청 키·온보딩은 보존하며 평가 백필이나 과거 일괄 재평가를 실행하지 않는다.

`npm run db:generate` 후 `npm run db:migrate:deploy`로 적용한다. 새 서버 시작 전에 마이그레이션을 완료한다. enum 추가는 PostgreSQL의 새 enum 값 사용 제약 때문에 명시적 트랜잭션 밖에서 실행하고 나머지는 BEGIN/COMMIT으로 적용한다. 운영 DB는 이번 구현 검증에 사용하지 않는다.

기존 deferred validator를 확장하여 self_assessment의 성인 연령·8개 허용 코드, 평가 JSON의 기록 ID·종목 코드·revision 일치를 검사한다. 과거 null 평가는 허용한다. API 수정은 부모 revision 잠금을 획득한 뒤 모든 종목의 평가를 다시 저장한다. 읽기는 Repeatable Read 스냅샷에서 저장된 평가를 반환하므로 기준 코드 변경만으로 과거 결과가 바뀌지 않는다.

## 2026-09-24 성인 윗몸말아올리기 신규 입력 제외

`20260924000100_retire_self_curl_up`은 이전 카탈로그에서 `self_curl_up`만 제외한 `nfa100-2026-09-24`를 추가한다. 전체 20개, 성인 16개, 청소년 15개이며 청소년 `curl_up`은 그대로다. 불변 카탈로그를 수정하거나 기존 측정 항목·평가·생성 요청 키를 삭제하지 않는다. 공식 수치 기준을 확보하지 못해 신규 입력에서 제외한다는 2026-09-24 사용자 결정을 반영한다.

서버는 카탈로그 버전·등록 방식에 관계없이 해당 코드의 신규 POST를 거절한다. PATCH는 잠금 후 읽은 현재 기록에 이미 있는 항목만 유지·수정·제거할 수 있고, 제거 후 재추가할 수 없다. 기존 생성 요청 재시도와 과거 조회는 유지한다. 이전 DB 검증 함수의 8개 코드 허용은 과거 항목을 보존하기 위해 유지하며, 현재 API의 간이측정 신규 입력 목록은 7개다. 저장된 과거 평가의 일괄 변경은 없다. 새 서버 시작 전에 `npm run db:migrate:deploy`로 새 카탈로그를 적용한다.
