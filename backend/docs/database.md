# DB 설계와 운영

PostgreSQL 17과 Prisma 7.10을 사용한다. 정밀한 측정값, 고유 키·외래키, 트랜잭션과 명시적인 마이그레이션을 사용하는 구조다.

## 계정과 측정 데이터

- `users`: 사용자 지정 5개 컬럼. 이메일은 정규화한 값으로 유일하며 이메일 인증 API가 입력 검증·Argon2id 해싱·응답 필드 제한을 처리한다. 이메일 소유 확인과 소셜 로그인은 후속 범위다.
- `auth_sessions`, `auth_refresh_tokens`, `auth_rate_limits`: 인증 세션, refresh token 해시·사용 이력, DB 기반 요청 제한. [인증 API](auth-api.md)를 참고한다.
- `measurement_catalogs`: 공식 자료 확인일과 버전. 실제 평가 기준 시행일과 구분한다.
- `measurement_definitions`: 출처 URL, 검사 방법, 단위, 적용 나이, 정수·소수·값 범위. 공개 검사 목록을 기준 데이터로 보관하며 사용자 결과는 생성하지 않는다.
- `measurements`: 사용자 ID, 실제 측정일, 측정 당시 나이, 원문 등급, 카탈로그 버전, revision.
- `measurement_items`: 검사별 실제 입력값. 고정 정밀도가 없는 NUMERIC을 사용하여 저장 시 자릿수 반올림을 피한다. Prisma Decimal은 JSON 직렬화 시 문자열이므로 후속 API 계약에도 이를 명시해야 한다.
- `measurement_create_requests`: 사용자별 생성 요청 키·정규화한 입력 해시·생성한 기록 연결. 기록 삭제 시 연결만 null로 바꿔 생성 재시도가 삭제를 되돌리지 않게 한다. 계정 삭제 시 함께 지운다.

Prisma 관계를 통한 조회는 비밀번호 필드를 포함할 수 있다. 인증 API는 공개 4개 필드만 직렬화하며, `/api/v1/auth/me`는 인증된 사용자 자신의 계정만 반환한다.

## DB가 보장하는 무결성

외래키로 실제 사용자·카탈로그·검사와 연결한다. 기록과 항목의 카탈로그 버전이 일치해야 하고 검사 단위도 일치해야 한다. 같은 회차의 검사 코드는 중복되지 않는다. 공식 검사 정의는 수정·삭제하지 않고 새 버전으로 추가한다.

Prisma가 표현하지 못하는 제약은 마이그레이션 SQL에 있다. 측정 당시 연령, 정수 횟수, 숫자 범위, 유한 숫자, 최소 한 항목을 검증한다. 부모와 항목을 같은 트랜잭션에서 만들 수 있도록 일부 제약은 커밋 시 검증한다. 항목 변경은 부모를 잠가 동시 삭제로 빈 기록이 생기지 않도록 한다. 트랜잭션의 중간에 항목을 교체할 수 있지만 최종 빈 기록은 커밋할 수 없다.

측정 수정 API는 `If-Match`와 현재 revision을 비교하고 전체 변경과 같은 트랜잭션에서 revision을 증가시킨다. 생성은 사용자별 요청 키로 중복을 막고, 모든 개인 기록 조회·변경은 인증된 사용자 ID로 제한한다. Decimal 값은 API에서도 문자열로 처리한다. [측정 API 계약](measurements-api.md)을 참고한다. 실제 분석 결과 적용은 후속 기능이다.

## 마이그레이션

1. `20260919000100_measurement_storage`: 공통 사용자 ID 기반과 측정 저장 테이블·제약.
2. `20260919000200_nfa100_catalog`: 출처를 확인한 검사 19개. 테스트 사용자나 측정 결과는 포함하지 않는다.
3. `20260919000300_account_schema`: 사용자 지시로 확정한 이메일 계정 5개 컬럼. 빈 이메일·임의 비밀번호를 backfill하지 않는다.
4. `20260919000400_auth_sessions`: 계정 컬럼을 유지하면서 세션·회전 토큰 이력·요청 제한 테이블을 추가한다.
5. `20260919000500_measurement_create_requests`: 요청 재시도 중복 방지와 삭제된 기록 재생성 방지를 위한 사용자별 요청 이력.

마이그레이션 1·2를 이미 로컬 DB에 적용한 뒤 계정 컬럼이 확정되어 3으로 추가했다. 기존에 적용한 파일을 다시 쓰거나 DB를 초기화하지 않았다. 사용자 ID만 있는 기존 운영 행이 존재한다면 마이그레이션 3 적용 전에 실제 이메일을 확보하는 별도 이행 작업이 필요하다. 마이그레이션 4는 기존 계정 행이나 비밀번호를 변경하지 않는다.

Prisma 스키마를 바꾼 후에는 개발 마이그레이션 초안을 확인하고 필요한 SQL 제약을 추가한다. 기존 마이그레이션은 수정하지 않는다. PostgreSQL 트리거·CHECK는 Prisma 스키마에 전부 표시되지 않으므로 SQL과 실제 DB 통합 테스트가 함께 기준이 된다. 운영에서 `db push`나 `migrate reset`으로 적용하지 않는다.

## 연결·테스트

앱은 환경변수의 접속 주소로 실제 DB에 연결하고 종료 시 풀을 정리한다. 풀 크기는 프로세스당 최대 5개, 연결 제한 5초, 쿼리 제한 10초다. 프로세스 수와 운영 DB의 연결 한도를 함께 고려해 조정한다. 접속 주소·비밀번호를 로그나 상태 확인 응답에 출력하지 않는다.

전용 테스트 DB에 임시 스키마를 만들고 모든 마이그레이션을 두 번 실행해 재적용도 확인한다. 테스트 종료 시 생성한 임시 스키마만 삭제한다. 중간 프로세스 강제 종료 시 `test_` 접두사의 잔여 스키마가 남을 수 있으며 자동으로 다른 스키마를 삭제하지 않는다.

## 의존성 고정

Prisma Client·PostgreSQL 어댑터·CLI를 7.10.0으로 맞췄다. 이 버전의 하위 패키지에서 보고된 재귀 병합 및 MySQL 드라이버 취약점 때문에 `@prisma/config`의 `deepmerge-ts`를 8.0.2, Prisma의 `mysql2`를 3.24.4로 제한해 override한다. 현재 서비스 DB는 PostgreSQL이다. 의존성 갱신 시 override 필요성과 공식 지원 범위를 다시 확인하고 스키마 생성·마이그레이션·실제 DB 테스트를 함께 실행한다.
