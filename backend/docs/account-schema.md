# 계정 스키마

작성일: 2026-09-19. 사용자가 지정한 계정 테이블의 컬럼은 아래 5개다. 계정 스키마를 먼저 정하고 측정·운동 기록은 계정 ID에 연결한다.

| 컬럼         | 형태               | 규칙                                                                    |
| ------------ | ------------------ | ----------------------------------------------------------------------- |
| `id`         | UUID, 기본키       | 서버/DB가 생성하는 서비스 내부 식별자                                   |
| `email`      | 문자열, 필수, 유일 | 로그인 이메일. 앞뒤 공백 제거·소문자화 후 저장                          |
| `password`   | 문자열             | 단방향 비밀번호 해시. 원문 비밀번호를 저장하거나 응답으로 반환하지 않음 |
| `created_at` | 시간대가 있는 시각 | 계정 생성 시각, DB 기본값 사용                                          |
| `updated_at` | 시간대가 있는 시각 | 계정 변경 시 갱신                                                       |

Prisma에서는 `createdAt`, `updatedAt`으로 다루고 실제 DB 컬럼은 `created_at`, `updated_at`으로 매핑한다. 측정 기록의 `user_id`는 `users.id`를 참조한다.

`password`에는 Argon2id 해시를 저장한다. 이메일 회원가입 API가 실제 입력 비밀번호를 해싱하며 응답에는 비밀번호·해시를 포함하지 않는다. 소셜 로그인만 사용하는 미래 계정을 위해 nullable은 유지한다. 임의의 기본 비밀번호를 만들어 채우지 않는다. Prisma Studio의 직접 입력은 해싱을 거치지 않으며, 인증 API는 평문·NULL 비밀번호로 로그인하지 못하게 한다. 소셜 제공자가 이메일을 반환하지 않는 가입 흐름은 후속 기능에서 실제 이메일 입력·확인을 설계하며 가짜 이메일로 계정을 생성하지 않는다.

## 별도 기능에 보존할 결정

- 닉네임은 중복을 허용한다. 로그인 이메일과 닉네임은 서로 다른 역할이다.
- 운동 목적은 여러 개를 선택할 수 있다. 실제 선택지 목록은 추천 기능을 설계하며 정한다.
- 닉네임·운동 목적·온보딩 진행은 이후 프로필 기능에서 관리한다. 이번 사용자 계정 테이블에 컬럼을 추가하지 않는다.
- 이메일·비밀번호 인증과 별도 세션 저장 구조를 구현했다. 카카오·구글 로그인·소셜 계정 식별자·이메일 확인은 후속 범위로 유지한다.
- 같은 이메일을 이유로 서로 다른 로그인 수단을 자동 연결하지 않는다.

## 구현 범위

DB 기반과 [회원가입·로그인·로그아웃·토큰 갱신·내 계정 조회](auth-api.md)를 구현하고 실제 PostgreSQL에서 검증한다. `auth_sessions`와 `auth_refresh_tokens`는 별도 테이블이며 사용자 테이블의 5개 컬럼은 바뀌지 않는다. [측정 기록 CRUD](measurements-api.md)에도 인증 가드와 사용자별 소유권 검사를 적용했다.

기존 요구사항 출처: [회원가입 / 로그인 / 온보딩 명세](https://app.notion.com/p/d54634ca4bdf83a8bb7c0147f51e63db), 2026-09-19 Notion 앱 확인. 계정의 최종 5개 컬럼(`id`, `email`, `password`, `created_at`, `updated_at`)·닉네임 중복·운동 목적 복수 선택은 현재 대화의 최신 사용자 결정이다. 중간에 언급된 별도 username 로그인은 최종 이메일 로그인 결정으로 대체했다.
